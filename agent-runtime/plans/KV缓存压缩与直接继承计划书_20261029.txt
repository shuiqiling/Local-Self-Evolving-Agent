KV 缓存压缩与直接继承计划书
版本：v1，待用户审核
日期：2026-10-29
状态：仅形成方案；未启动本方案的代码修改、Ubuntu 部署、训练或性能测试。

一、目标和“压缩”的定义

目标流程只有一条：
原窗口已有 K/V → 选择保留集合 → 压实 K/V 和缓存元数据 → 下一逻辑窗口直接继承 → 仅计算新输入。

第一版采用“选择性 KV 压缩”：保留选中 token 的原有 K/V，淘汰其余缓存项。属于有损容量压缩，保留向量不经过文字摘要转换，也不重新前向计算。它不保证把全部历史含义无损融合成更少的新向量。

这里必须由用户审核压缩定义。如果预期是“所有历史内容融合成更少的潜在向量”，那属于另一类压缩器/模型适配路线，本计划不能宣称已经覆盖。

本方案不会把 KV 量化、单纯固定前缀命中、删除后重新预填历史，算作完成上述目标。第一版保持现有 KV 精度，以便单独测量选择压缩的影响。

切窗快速路径不调用 4B 生成交接摘要，不自动注入上一轮新增的原文锚点，也不增加 LoRA 训练。历史存档、索引检索和按需读档继续保留，但它们与切窗本体分开计时。

二、基线与适用范围

以目前使用的 Qwen3-4B-Instruct-2507 Q4_K_M、concise-v2、现有 VNNI 推理库为起点；实际文件哈希、KV 类型、模板、编译参数在执行第一阶段时重新核对。

同一主 Agent 流中的模型、LoRA 及其 scale、分词器、模板和缓存格式必须一致。辅助角色使用自己的上下文，不把基础模型或另一适配器的 KV 接入主 Agent。

当前暂停版本包含尚未完成验收的修改，不能直接称为正确性基线。执行前先记录当前部署和回退点，选择同一份固定提示词用于全部对照，不边测边修改提示词。

第一版只实现一条选择压缩路线。SnapKV、PyramidKV 等作为研究参考，不在没有说明的情况下另加一套算法、换框架或扩大训练任务。

三、建议的缓存预算

初始建议值，待审核：
  工作输入预算：3072 个有效 KV 位置。
  输出预留：沿用主模型最多 384 tokens，单列计算。
  压缩后默认保留：2048 个 KV 位置。
  更强压缩档：1536；只有 2048 档通过验收后才考虑。
  正式后端物理容量：先沿用每流 8192，实际配置执行前核对。

触发条件：在处理新输入前，若“当前有效 KV 数＋本次新增输入 tokens”将超过 3072，则先压缩；生成还需单独检查输出预留和物理容量。

短窗口指有效 KV 数及实际注意力访问范围缩短，不表示把累计位置编号强行清零。累计位置仍受模型及后端支持范围限制，不宣称无限上下文。

四、第一版如何选择保留的 KV

保留集合按消息和工具事件分组，尽量完整保留条件、否定、更正及工具调用/结果配对，不任意把一句话截成几个孤立 token。

优先级：
  1. 保护固定系统规则、工具定义、当前有效约束和未结束的工具交互。
  2. 保护最新完整用户轮次及最近一段连续上下文，近期区初始预算为 512–768 tokens。
  3. 剩余预算保留程序元数据能明确指向的当前任务证据、最新状态版本和必要的历史事件组。
  4. 更旧、未被上述规则保护的记录优先淘汰；保留项仍按原始时间顺序排列。

只使用已有的来源、状态版本和操作账本等元数据，不假装程序已经理解任意自然语言事实之间的覆盖关系。没有结构化更正关系时，不能宣称已自动消除全部矛盾。

第一版采用所有层/头共享的保留位置集合，适配现有缓存结构。这不是原样复现 SnapKV 的逐头选择。注意力打分、逐头预算或学习型合并如果成为必要条件，需要另列成本和改动范围，不能悄悄加上。

保护区和完整事件组若超过目标预算，不强行删除关键状态。报告实际最低可保留量；若无法同时满足窗口上限和保护要求，该配置判为不满足目标。

五、缓存如何直接交给下一窗口

1. 在没有正在执行的 decode 的边界冻结当前流，记下已处理事件序号和窗口版本；期间到达的新消息进入待处理队列。
2. 建立 K/V 与来源事件、逻辑 token 位置、物理 cell 的对应表，计算保留集合。
3. 将保留的 K/V 行压实到连续物理区域，并同步更新元数据、因果 mask 和分配器；回收淘汰项。
4. 保持保留 token 原来的逻辑位置及相应 RoPE 状态。第一版不把位置直接改成 0…保留长度，也不默认使用位置除法压缩。
5. 应用层窗口 ID 增加，但下一窗口继承同一主流缓存句柄及版本。正常路径优先原位继承，避免跨进程、跨 stream 整个缓存复制。
6. 下一次推理只追加尚未计算的新消息、必要边界 tokens、检索索引或模型主动读取的工具结果。已保留 token 的前向计算次数必须为零。
7. 验证新缓存后提交窗口映射，并处理冻结期间的新消息；操作账本不因换窗重置，已完成动作不重放。

下一窗口是新的应用窗口，不等于必须重新创建模型上下文。若采用新的 sequence ID，要单独验证缓存共享与旧 sequence 释放，不能保留旧完整缓存后声称已经节省空间。

六、必须修改的后端与请求协议

当前程序每次构造完整提示词，原 server 的前缀匹配可能因历史被裁剪而清掉缓存并重新预填。因此不能仅靠 cache_prompt 或槽位参数实现本方案。

计划增加独立的有状态增量接口：session_id、window_id、配置指纹、新消息及压缩操作。Agent 在首次建立流时输入固定前缀，后续只追加增量；原网页和任务存档通过适配层接入。

必须验证增量聊天模板、消息边界及工具交互编码。在未压缩对照中，增量 token 序列应与选定模板的完整编码一致，不能在边界上重复/漏加 token。

源码核对已确认：当前版本提供按序列删除、复制及位置操作，但同 stream 与跨 stream 复制行为不同；注意力长度使用最高已占用 cell 进行对齐计算；复用缓存单元还有连续位置假设。因此，删除记录、调用复制 API 或减少计数都不足以证明完整实现。[1][2]

需要补齐或验证：
  - 允许所选逻辑位置有间隔，避免后端自动清掉本应保留的历史位置；
  - 物理压实真正降低后续注意力扫描范围，而非留下大片 masked 空洞；
  - K/V 实际张量布局、缓存类型、Flash Attention 和 VNNI 兼容；
  - 计数器分别记录有效位置、实际扫描长度、预分配字节数及进程 RSS。

原版本预分配的缓冲可能不立即缩小 RSS。因此“有效 KV 变少”和“操作系统内存下降”分开报告，不能混为一项收益。

七、执行阶段与停止条件

A. 核对与隔离
保存模型、LoRA、源码、VNNI 补丁、编译参数、模板、服务及回滚点的指纹；在独立目录、进程/端口及测试数据库中工作，不原地重建当前运行库。
产物：可行性核对表及准确的代码改动清单。

B. 零压缩继承
先保留 100% KV，仅切换逻辑窗口，证明没有重新预填历史，且保留 K/V 数值及贪心输出与未切窗对照一致。
停止条件：需要重新计算旧 token 才能续推，或没有压缩却改变输出，先修后端，不进入质量测试。

C. 真正的选择与压实
实现 3072→2048，校验保留行、位置、mask、扫描长度和新 token 追加；单纯前缀＋近期窗口仅作调试检查，不冒充完整保留策略。
停止条件：不能安全支持位置间隔、实际扫描范围不缩短、保留 KV 被重新前向计算，或必须关闭关键优化而未说明代价。

D. Agent 集成与对照
新模式停用文字交接摘要及此前错误路线的自动锚点补丁；接入增量消息、版本校验和工具账本。使用固定提示词、同一模型/LoRA/种子和成对相同输入，不再通过更换随机任务 ID 或提示词掩盖差异。

E. 验收和部署
先提交结果、失败样本及最终配置。仅在达到事先约定的门槛后切换正式服务，保留开关及旧库回退路径。需要更换框架、训练压缩器或扩展算法范围时，重新提交计划供审核。

八、测试设计

正确性参考：同一输入、同一初始 KV 检查点的“未压缩直接续推”。上一轮文字摘要切窗只作历史耗时参考，不能作正确答案标准。

A/B 使用独立缓存实例，避免共享引用让内存节省成为假象。所有数据和期望答案先冻结。开发失败样本与最终验收样本分开；所有尝试保留，不只汇报最好的一次。

检查分三层：
  1. 机制：零压缩继承、保留行一致、位置/mask、只计算新输入、任务与适配器隔离、取消和恢复。
  2. 单次质量：30 道固定验收问题，覆盖数值连续更正、否定与条件、对象区分、用户计划顺序、已完成/未完成及无答案。
  3. 长程：至少 20 次连续切窗，检查事实与计划漂移、账本去重、权限和迟到消息；不能只测一到两窗。

未压缩参考必须能容纳完整测试流。若超出 8192，另设足够大的隔离参考容量并明确记录；公平的速度对照使用相同物理容量，不截断参考历史。

KV 内的记忆与读档恢复分开统计：一组只测直接继承保留了什么；另一组允许现有记忆工具，核对是否正确判断需要读档。不能用检索补回的答案冒充 KV 已完整保留。

九、指标和建议验收门槛

必须记录：
  - T_switch：从冻结到下一窗口可接收新输入，包含筛选、快照/复制、压实、位置/mask 更新和提交；
  - TTFT：新请求到首个输出 token；
  - T_answer：新请求到完整答案；
  - 本轮新增 token 的实际预填 TPS、输出 TPS、旧 token 重算数量；
  - 保留 KV 数、实际扫描长度、分配内存、RSS、峰值临时内存；
  - 依据冻结原文逐条检查的事实、条件、更正、计划和实际工具执行次数。

建议门槛，均为待审核目标而非已实现结果：
  - 切窗生成摘要次数为 0，保留旧 token 的重新前向计算次数为 0。
  - 3072→2048 后有效 KV 确实减少约三分之一，扫描长度按后端对齐规则同步缩短。
  - 至少 100 次覆盖不同输入长度的切窗本体计时；目标 P50≤1 秒、P95≤2 秒。必须报告样本数、冷/热状态与复制成本，不预先承诺倍数提速。
  - 关键更正、约束、计划顺序和操作去重用例全部通过；单个关键状态失败就不进入正式部署。
  - 本批完整答案率不出现相对未压缩参考的下降；30 题筛选通过不能宣称总体准确率或统计上的无损。
  - 后端改造的零压缩对照若明显拖慢原有输入/输出速度，先说明并解决，不靠改模型、LoRA或输出上限获得表面优势。

十、失败、恢复和审核边界

压缩是有损操作，可能丢失未保护的信息；保留部分 KV 不等于拥有全部旧文本。被淘汰内容仍保存在原文存档，可以按需检索。

模型/LoRA/模板/缓存格式改变、缓存损坏或进程重启时，旧缓存不能直接冒充有效。恢复路径及重建成本单列，不计为快速切窗成功。

切窗采用可回退的事务；快照复制时间和峰值内存计入指标。失败保留或恢复上一份有效缓存，不静默退回“生成摘要再预填”后继续报告本方案成功。

本次待审核的关键选择：
  1. 压缩定义采用“选择保留既有 KV”，接受其有损性质，而非全部历史语义融合。
  2. 默认从 3072→2048 开始，1536 留待更强压缩阶段。
  3. 先通过零压缩继承和真实扫描长度缩短，再做完整 Agent 评测。
  4. 本文件获审前继续保持测试暂停；批准方案也不等于提前验收任何尚未实现的速度或准确率。
